## 1. 文書の目的

本書は、Condition Pulse v0.1.2を基礎として、長期利用時の安心感、回答体験、アプリ更新の確実性、蓄積データから得られる気づきを改善するv0.2の改修仕様を定義する。

v0.2では、機能数を増やすこと自体を目的としない。以下を重点とする。

1. 記録を失いにくくする
2. 誤操作を修正できるようにする
3. 答えにくい質問をユーザー自身で調整できるようにする
4. PWAの更新をユーザーに分かる形で適用する
5. 点数ではなく、観測の充足度と一日の変化の型を示す
6. 改修による回帰を自動テストで検出する

本アプリは引き続き、病気の診断、疾病リスクの算定、受診判断、治療提案を行わない。

## 2. 現状と課題

v0.1.2では、以下が実装済みである。

- 1回3問、朝・昼・夜のチェックイン
- 66問の日本語質問バンク
- 時間帯、未観測領域、前回回答等を用いた質問選択
- IndexedDBによる端末内保存
- 今日の流れ、7日間の傾向、履歴
- JSON / CSV書き出し
- Service Workerによるオフライン基本対応
- 個人・時間帯別の平常値との比較
- 安全案内

一方、長期利用に向けて次の課題がある。

- JSONを書き出せるが、復元できない
- 誤タップ後に回答を修正しにくい
- 答えにくい質問を非表示にできない
- 新版が配信されても、古いService Workerが残っているか分かりにくい
- 「平常値を学習中」からどこまで観測が進んだか分かりにくい
- 7日間の平均だけでは、一日の流れの特徴が十分に伝わらない
- GitHub Actionsがなく、質問バンクや静的資産の回帰を自動検出できない

## 4. 設計原則

### 4.1 既存データを壊さない

v0.2は、v0.1.2のIndexedDBに保存されたセッションと設定をそのまま読み込めることを必須とする。

IndexedDBの既存ストア構造は変更しない。

- `sessions`
- `settings`

新しい情報は、既存設定の追加プロパティまたはセッションの任意プロパティとして保存する。DBバージョンの更新は行わない。

### 4.2 端末内完結を維持する

バックアップの読み込み、検証、統合、パターン分析は、すべてブラウザ内で実行する。ファイル内容や回答履歴を外部へ送信しない。

### 4.3 変更はユーザー操作を起点とする

以下を自動実行しない。

- バックアップファイルによる既存データの置換
- アプリ更新による入力中データの破棄
- 質問の自動永久非表示
- 過去記録の自動削除

### 4.4 不確実性を表現する

観測充足度は医学的な信頼度ではない。変化パターンは因果関係や健康状態の判定ではない。

表示では以下を避ける。

- 精度95%
- 健康度が上がった
- 睡眠不足が原因である
- ストレス状態である

代わりに、観測できた事実と対象期間を示す。

> この14日間では、朝に低めでも昼に戻る日が比較的多く見られました。

## 6. F-01 JSONバックアップの読み込み・復元

### 6.1 目的

端末変更、SafariのWebサイトデータ削除、PWA再インストール等で記録を失った場合に、JSONバックアップから復元できるようにする。

### 6.2 バックアップ形式

v0.2から、JSONの先頭に形式識別情報を追加する。

```json
{
  "format": "condition-pulse-backup",
  "schemaVersion": 2,
  "exportedAt": "2026-07-29T00:00:00.000Z",
  "appVersion": "0.2.0",
  "questionBankVersion": "2026-07-28",
  "settings": {},
  "sessions": []
}
```

v0.1系の書き出しには `format` と `schemaVersion` がないため、以下の条件を満たす場合は旧形式 `schemaVersion: 1` とみなして読み込み可能とする。

- ルートがオブジェクト
- `sessions` が配列
- `settings` がオブジェクト
- `exportedAt` が存在する

### 6.3 ファイル選択

設定画面のデータ欄に以下を追加する。

- `JSONバックアップを読み込む`
- 非表示の `<input type="file" accept="application/json,.json">`

ファイルはブラウザ内で `File.text()` により読み込む。

初期上限は10 MBとする。上限を超える場合は処理せず、理由を表示する。

### 6.4 検証

読み込み後、保存前に次を検証する。

#### ルート

- JSONとして解析できる
- オブジェクトである
- 対応するバックアップ形式である
- `sessions` が配列である
- セッション件数が異常に多くない

#### セッション

最低限、以下を確認する。

- `id`: 空でない文字列
- `localDate`: `YYYY-MM-DD`
- `timeBand`: `morning | daytime | evening`
- `sessionType`: `scheduled | ad_hoc`
- `startedAt`: 有効な日時
- `completedAt`: 有効な日時
- `responses`: 配列
- `responses[].questionId`: 空でない文字列
- `responses[].selectedIndex`: 0〜4の整数
- `responses[].normalizedValue`: -2〜2の数値

不明な任意プロパティは保持してよいが、画面表示時は必ずエスケープする。

#### 設定

設定は既知のキーのみ採用する。

- `locale`
- `timeZone`
- `timeBands`
- `reducedMotion`
- `privacyMode`
- `onboardingCompleted`
- `questionPreferences`

未知のキーは無視する。

### 6.5 復元方式

ユーザーは次の2方式を選べる。

#### 追加・統合

初期選択とする。

- 既存セッションを保持する
- `session.id` が未登録のものだけ追加する
- 同じIDがある場合は既存データを優先し、読み込み側をスキップする
- 設定は原則として既存設定を維持する
- 質問表示設定のみ、ユーザーが明示的に選んだ場合に統合できる

#### 置き換え

詳細操作として提供する。

- 既存セッションと設定をバックアップ内容で置き換える
- 二段階確認を行う
- 実行前に現在データのJSON書き出しを強く案内する
- 置換処理は単一IndexedDBトランザクションで行う

### 6.6 プレビュー

保存前に次を表示する。

```text
バックアップを確認しました

記録: 184件
期間: 2026年7月28日〜2026年9月30日
重複: 12件
追加予定: 172件
設定: 含まれています
```

この時点ではIndexedDBを変更しない。

### 6.7 原子性

`storage.js`に次を追加する。

```js
importSnapshot({ sessions, settings, mode })
```

`sessions` と `settings` を同一の `readwrite` トランザクションで処理する。途中でエラーが発生した場合はトランザクションを中止し、既存データを維持する。

### 6.8 完了表示

```text
バックアップを読み込みました
追加: 172件
重複のためスキップ: 12件
```

失敗時は、既存データが変更されていないことを明示する。

### 6.9 受入基準

- v0.1形式とv0.2形式を読み込める
- 不正JSONを読み込んでも既存データが変わらない
- 追加方式で重複セッションが増えない
- 置換方式が途中失敗した場合にロールバックされる
- 読み込み内容が外部へ送信されない

## 7. F-02 回答の修正・取り消し

### 7.1 目的

短時間回答による誤タップを、履歴全体を編集可能にせず修正できるようにする。

### 7.2 回答中の修正

2問目以降の画面に `一つ前へ` を表示する。

操作時は以下を行う。

1. `activeIndex` を1減らす
2. 直前のresponseを一時配列から取り除く
3. 直前質問を再表示する
4. 再回答された値でresponseを作り直す

セッション完了前のため、IndexedDBには影響しない。

### 7.3 完了直後の修正

完了画面に以下を追加する。

- `回答を修正`
- `この記録を取り消す`

#### 回答を修正

- 現在のセッションだけを編集対象とする
- 同じセッションIDを維持する
- 3問を既存回答付きで再表示する
- 保存時に `revision` を1加算する
- `editedAt` を記録する
- フィードバックと安全シグナルを再計算する
- `saveSession()` の `put` で上書きする

#### この記録を取り消す

- 確認ダイアログを1回表示する
- `deleteSession(sessionId)` でIndexedDBから削除する
- メモリ上の `state.sessions` からも削除する
- ホームへ戻る

完了画面を離れた後は、v0.2では履歴から編集・削除できない。

### 7.4 状態遷移

```text
idle
  ↓
answering
  ├─ back → answering
  ├─ close → idle
  └─ complete → completed
                    ├─ edit → editing → completed
                    ├─ discard → idle
                    └─ leave → idle
```

### 7.5 セッション追加項目

既存セッションに任意項目を追加する。

```json
{
  "revision": 1,
  "editedAt": "2026-07-29T00:00:00.000Z"
}
```

旧セッションは `revision: 0` とみなす。

### 7.6 受入基準

- 2問目・3問目から前の質問へ戻れる
- 戻って再回答してもresponseが重複しない
- 完了直後の編集で同じセッションIDが維持される
- 編集後にフィードバックが再計算される
- 取り消した記録がホーム、今日、履歴、傾向から消える
- 過去の他セッションは編集できない

## 8. F-03 質問の表示頻度設定

### 8.1 目的

答えにくい、当てはまらない、繰り返しが負担になる質問を、ユーザー自身で調整できるようにする。

### 8.2 設定値

`DEFAULT_SETTINGS`に以下を追加する。

```js
questionPreferences: {}
```

保存形式:

```json
{
  "questionPreferences": {
    "cognitive_focus_001": {
      "mode": "reduced",
      "updatedAt": "2026-07-29T00:00:00.000Z"
    },
    "social_reply_002": {
      "mode": "hidden",
      "updatedAt": "2026-07-29T00:00:00.000Z"
    }
  }
}
```

`mode`:

- `normal`: 通常
- `reduced`: 出現頻度を減らす
- `hidden`: 表示しない

設定が存在しない質問は `normal` とみなす。

### 8.3 回答画面からの操作

質問画面に小さな `この質問について` ボタンを置く。

押下時に次を表示する。

- この質問を減らす
- 今後表示しない
- 何もしない

#### この質問を減らす

現在の質問には回答できる。次回以降、質問選択スコアにペナルティを加える。

```text
preferencePenalty = -8
```

十分な代替質問がない場合は、選ばれる可能性を残す。

#### 今後表示しない

- 現在の質問は回答せずスキップできる
- 同じセッション内で代替質問を1問選ぶ
- スキップは回答として保存しない
- 代替候補がない場合は、非表示化を中止して説明する

### 8.4 質問選択ロジックへの反映

`selectQuestions()`に `questionPreferences` を渡す。

```text
候補抽出
  ├─ hidden → 除外
  ├─ reduced → スコア -8
  └─ normal → 変更なし
```

アンカー質問がすべて非表示になっても、チェックイン不能にしない。

- 組み込みの標準アンカーをフォールバックとして使う
- 最低3問を確保できない場合は、`reduced` を候補へ戻す
- `hidden` は原則として戻さない

### 8.5 設定画面

`質問の表示設定` セクションを追加する。

- 頻度を減らした質問
- 非表示の質問
- 個別に通常へ戻す
- すべての質問設定をリセット

質問文は必ずHTMLエスケープして表示する。

### 8.6 バックアップ

`questionPreferences`はJSONバックアップへ含める。CSVには含めない。

### 8.7 受入基準

- hiddenの質問が次回以降選ばれない
- reducedの質問が通常質問より低頻度になる
- 現在質問をhiddenにした場合、3問構成が維持される
- 質問設定をすべてリセットできる
- 設定後もアンカー質問が必ず1問提示される

## 9. F-04 Service Worker更新通知

### 9.1 目的

新版が配信されたことをユーザーに知らせ、入力中データを失わず、明示的に更新できるようにする。

### 9.2 更新フロー

`update-manager.js`でService Worker登録を管理する。

```text
アプリ起動
  ↓
register('./sw.js')
  ↓
registration.update()
  ↓
updatefound
  ↓
新SWが installed かつ既存controllerあり
  ↓
「新しいバージョンがあります」表示
  ↓
ユーザーが「更新」
  ↓
waiting SWへ SKIP_WAITING
  ↓
controllerchange
  ↓
1回だけ reload
```

### 9.3 Service Worker側

`sw.js`にメッセージ受信を追加する。

```js
self.addEventListener('message', event => {
  if (event.data?.type === 'SKIP_WAITING') self.skipWaiting();
});
```

### 9.4 更新バナー

画面下部ナビゲーションの上に、非モーダルの更新バナーを表示する。

```text
新しいバージョンがあります
[あとで] [更新]
```

要件:

- `role="status"`
- キーボード操作可能
- 画面幅320pxでも横スクロールしない
- 安全領域を考慮する
- 更新を拒否してもアプリを使い続けられる

### 9.5 回答中の扱い

回答中または完了直後の未確定編集がある場合、即時再読み込みしない。

更新ボタン押下時:

```text
回答中です。記録を終えた後に更新します。
```

`pendingUpdate = true` とし、保存または破棄後に更新処理を再開する。

### 9.6 キャッシュ戦略

現行の全GETに対するcache-firstを見直す。

#### ナビゲーション

network-firstとする。

1. ネットワークから最新HTMLを取得
2. 成功時にキャッシュ更新
3. オフライン時はキャッシュ済み `index.html` を返す

#### 同一オリジン静的資産

cache-firstとし、キャッシュ名をアプリバージョンで更新する。

#### 外部リンク

Service Workerで処理しない。

### 9.7 更新確認頻度

- 起動時に1回 `registration.update()`
- 同一タブ内では過剰に繰り返さない
- 30分以上バックグラウンドだった後に復帰した場合、1回再確認してよい

### 9.8 受入基準

- 新Service Worker待機時に更新バナーが表示される
- 更新ボタンで新版へ1回だけ再読み込みされる
- 回答中に更新しても回答が消えない
- オフライン起動を維持する
- IndexedDBの回答履歴が更新で消えない

## 10. F-05 観測充足度

### 10.1 目的

「平常値を学習中」という一種類の表示ではなく、どの時間帯の観測がどこまで進んだかを、過度な精密さを避けて示す。

これは統計的信頼度や医学的精度ではなく、記録の量と分布を示すUX指標である。

### 10.2 表示段階

全体と時間帯別に4段階を定義する。

| 状態 | 表示 | 目安 |
|---|---|---|
| `starting` | 観測を始めたところ | 記録が少ない |
| `forming` | 傾向が見え始めています | 複数日に記録あり |
| `usable` | 時間帯比較に使える記録があります | 7日以上かつ一定数 |
| `stable` | 基準が比較的そろっています | 14日以上かつ各時間帯に記録あり |

### 10.3 全体判定

初期閾値:

```text
starting:
  totalSessions < 3

forming:
  totalSessions >= 3

usable:
  uniqueDays >= 7
  AND totalSessions >= 10

stable:
  uniqueDays >= 14
  AND totalSessions >= 24
  AND eachTimeBandSessions >= 5
```

### 10.4 時間帯別判定

```text
starting:
  bandSessions < 2

forming:
  bandSessions >= 2

usable:
  bandSessions >= 5
  AND bandUniqueDays >= 5

stable:
  bandSessions >= 10
  AND bandUniqueDays >= 10
```

閾値は医学的基準ではなく、表示の安定性と分かりやすさのための初期値である。

### 10.5 実装

`readiness.js`に以下を実装する。

```js
calculateReadiness(sessions)
calculateBandReadiness(sessions, timeBand)
getNextReadinessHint(readiness)
```

主分析では `scheduled` を優先し、`ad_hoc` は全体件数には含めても、時間帯の安定判定では補助扱いとする。

### 10.6 表示

ホーム:

```text
昼の傾向が見え始めています
昼の記録があと2回ほどあると、時間帯比較がしやすくなります。
```

傾向画面:

- 朝: 基準が比較的そろっています
- 昼: 傾向が見え始めています
- 夜: 観測を始めたところ

パーセント表示やゲージによる擬似的な精密さは避ける。

### 10.7 一日の回答数のフィードバック

ホームでは回答数に応じて表示を変える。

- 0回: `今の調子を小さく残してみましょう`
- 1回: `もう一つの時間帯があると、一日の変化が見えやすくなります`
- 2回: `今日は十分な観測ができています`
- 3回以上: `朝・昼・夜の流れがそろいました`

3回を義務にしない。

### 10.8 受入基準

- 記録件数と日数に応じて段階が切り替わる
- 欠測を悪化として扱わない
- 2回回答で肯定的な完了表示になる
- 医学的精度を示す表現を使わない

## 11. F-06 一日の変化パターン

### 11.1 目的

単純な平均値ではなく、朝・昼・夜の動き方を、ユーザーが理解しやすい短文で示す。

### 11.2 対象データ

基本対象:

- 直近14日
- `scheduled` セッション
- 同一 `localDate` 内の2時間帯以上の記録
- アンカー質問または対象領域の正規化値

`ad_hoc` は自己選択による偏りが大きいため、主要パターンの判定から除外する。将来、補助表示へ利用してよい。

### 11.3 前処理

各日、各時間帯、各領域についてセッション値を算出する。

```text
dailyValue(localDate, timeBand, domain)
```

同一領域に複数回答がある場合は中央値を用いる。

本人基準が利用可能な場合:

```text
deviation = dailyValue - baselineMedian(timeBand, domain)
```

基準が不足する場合はパターン表示を保留する。

### 11.4 初期パターン

#### P-01 朝は低めでも昼に戻る

```text
morning deviation <= -0.75
AND daytime - morning >= 0.75
```

表示例:

> この14日間では、朝に低めでも昼に戻る日が比較的多く見られました。

#### P-02 午後から夜に下がりやすい

```text
evening - daytime <= -0.75
```

表示例:

> この14日間では、昼から夜にかけて余力が下がる日が比較的多く見られました。

#### P-03 一日を通して安定

```text
max(bandValues) - min(bandValues) <= 0.5
AND all deviations between -0.75 and 0.75
```

表示例:

> この14日間は、朝から夜まで大きく揺れない日が多めでした。

#### P-04 夜に緊張が残りやすい

対象領域: `tension_recovery`

```text
evening deviation <= -0.75
```

表示例:

> 夜の「緊張と切替」が普段より低めの日が、最近いくつか見られました。

#### P-05 低めが一日続く

```text
at least 2 bands deviation <= -0.75
AND no recovery delta >= 0.5
```

表示例:

> この14日間では、低めの状態が次の時間帯まで続く日がいくつかありました。

### 11.5 表示条件

偶然の1日を傾向として扱わない。

初期条件:

- 対象期間に評価可能な日が4日以上
- 同じパターンが3日以上
- 評価可能日の60%以上

条件を満たさない場合は表示しない。

### 11.6 優先順位

同時に複数パターンが成立する場合、最大2件まで表示する。

優先スコア例:

```text
patternScore = occurrenceRate * eligibleDays * averageStrength
```

負のパターンだけが並ばないよう、安定または回復パターンが成立している場合は一つを優先する。

### 11.7 表現規則

使用する:

- 見られました
- 多めでした
- 一緒に現れることがありました
- この14日間では

使用しない:

- 原因です
- 病気の兆候です
- 必ず悪化します
- 自律神経が乱れています
- 休むべきです

### 11.8 受入基準

- 1日だけの変化ではパターン表示されない
- 最低データ条件を満たさない場合は保留表示になる
- 最大2パターンまで表示される
- scheduledとad_hocを混同しない
- 因果関係や診断を示す文面を出さない

## 12. F-07 GitHub Actions

### 12.1 目的

質問バンク、JavaScript、Service Worker、静的資産の不整合を、PRの段階で検出する。

### 12.2 ワークフロー

`.github/workflows/condition-pulse.yml`

トリガー:

- `pull_request`
- `push` to `main`

対象パス:

- `condition-pulse/**`
- `.github/workflows/condition-pulse.yml`

### 12.3 必須ジョブ

Node.js 20を使用し、次を実行する。

```bash
npm test
npm run validate:questions
npm run validate:assets
npm run check:syntax
```

#### 質問検証

- JSONとして解析可能
- ID重複なし
- 必須項目あり
- domainが既知値
- responseScaleが既知値
- directionが既知値
- timeBandsが有効
- active質問が60問以上

#### 静的資産検証

- `index.html`が参照するローカルファイルが存在する
- `sw.js`のAPP_SHELLに記載されたファイルが存在する
- APP_SHELLに重複なし
- Service Workerキャッシュ名とAPP_VERSIONが一致する

#### 構文検証

全JavaScriptを `node --check` 相当で確認する。

### 12.4 ブラウザスモークテスト

第二段階としてPlaywrightを導入する。

確認項目:

- 初回オンボーディング
- 3問回答と保存
- 再読み込み後の履歴保持
- 設定画面で横スクロールが発生しない
- JSON読み込みプレビュー
- 更新バナー表示の模擬

対象:

- Chromium mobile viewport
- WebKit mobile viewport

Playwright WebKitはiPhone実機の完全な代替ではないため、iOS Safari実機確認は引き続き必要とする。

### 12.5 受入基準

- PR作成時に必須ジョブが自動実行される
- 質問ID重複でCIが失敗する
- Service Workerの存在しないキャッシュ資産でCIが失敗する
- JavaScript構文エラーでCIが失敗する

## 13. データモデル

### 13.1 IndexedDB

```text
DB_NAME = condition-pulse
DB_VERSION = 1
stores:
  sessions
  settings
```

### 13.2 設定の追加項目

```js
const DEFAULT_SETTINGS = {
  // existing fields
  questionPreferences: {}
};
```

既存設定読み込み時は、現在と同様にDEFAULT_SETTINGSとマージする。

### 13.3 セッションの追加任意項目

```json
{
  "revision": 0,
  "editedAt": null
}
```

### 13.4 バックアップ形式とDB形式の分離

`schemaVersion`はバックアップファイルの形式であり、IndexedDBの `DB_VERSION` とは別である。

- Backup schema: 2
- IndexedDB version: 1

## 16. プライバシーと安全

### 16.1 バックアップ

バックアップには私的な健康回答が含まれる。読み込み・書き出し画面でその旨を明示する。

ファイルを外部サーバーへ送信しない。

### 16.2 インポートデータ

インポートされたタグや文字列を `innerHTML`へ直接挿入しない。既存の `escapeHtml()` またはDOMの `textContent` を使う。

### 16.3 パターン表示

観測パターンを疾病、受診要否、勤務能力と結び付けない。

### 16.4 データ削除

全削除とバックアップ置換は明確に区別する。復元操作から意図せず全削除へ遷移させない。

## 17. エラー処理

| 状況 | 表示・処理 |
|---|---|
| JSON解析失敗 | ファイルを読み込めない旨を表示。DB変更なし |
| 未対応形式 | 対応外のバックアップ形式と表示 |
| 一部セッション不正 | 原則として全体を拒否。詳細件数を表示 |
| IndexedDB書込み失敗 | トランザクション中止。既存データ維持 |
| 質問代替なし | 非表示化せず、代替質問がない旨を表示 |
| SW更新失敗 | 現在版を継続。再読込を強制しない |
| パターン計算データ不足 | 傾向を判断する記録がまだ少ないと表示 |
